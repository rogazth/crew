# E2e sin robar el foco

**Propuesto el 2026-09-26. Nada construido.** En macOS, `npm run e2e` abre y
cierra la app de verdad: cada `launchCrew` activa Electron y se lleva el foco.
En Linux el runner ya corre bajo Xvfb cuando no hay `DISPLAY`. Además
`scripts/e2e.mjs` fuerza `--test-concurrency=1`, un archivo por vez, y cada
archivo levanta un Chromium.

## Decisiones

### La ventana no se muestra

`launch()` en `e2e/harness.ts` exporta `CREW_E2E=1` junto a
`CREW_RENDERER=dist`. `restart()` pasa por el mismo `launch()`, así que un
relanzamiento también queda oculto.

Sin esa variable, la app de desarrollo abre la ventana como hoy.

En `electron/main.ts`, con `CREW_E2E=1` y solo en darwin,
`app.setActivationPolicy("accessory")` corre antes de `app.whenReady()`.
`accessory` no entra al Dock ni se activa al crear la ventana. `prohibited`
no puede crear ventanas.

`createWindow()` usa `show: false` y deja el tamaño en 1280×800 (el mínimo
es 800×520). Una ventana de 0×0 cambia el layout. Moverla fuera de la
pantalla, bajarle la opacidad o pasarle `--headless` a Electron sigue
activando la app.

Playwright habla con la página por CDP. `firstWindow()` recibe una ventana
oculta. Los atajos van por `page.keyboard` y `returnToWindow` ya manda
`blur` y `focus` sintéticos, porque Xvfb tampoco tiene gestor de ventanas.

Tras el primer `firstWindow()`, el harness afirma desde el proceso principal
que esa `BrowserWindow` no está visible (`isVisible() === false`). La forma
de `evaluate` se confirma contra el `playwright-core` instalado.

Un diálogo nativo (`dialog.showOpenDialog`) con la ventana oculta no tiene
a quién pegarse. Las e2e de hoy no llaman a `dialog-open`. Si un escenario
lo necesita, esa corrida muestra la ventana. El diálogo no se stubbea.

### Tres archivos a la vez

`--test-concurrency` limita procesos de archivo, no tests dentro de un
archivo. Cada `launch()` ya tiene su sandbox corto en `/tmp/ce-…`, con su
`HOME`, su `crewd` y su socket. Entre archivos no comparten estado.

Dentro de un archivo los tests siguen en serie. Varios archivos arman una
sola `Crew` en `before()`, y un test paralelo del mismo proceso la pisaría.
No se pone `concurrency: true` en `test` ni en `describe`.

El default pasa de 1 a 3. Hay un solo flag: si quien corre el script ya
pasó `--test-concurrency`, ese valor es el que se usa. 3 y no todos los
núcleos, porque cada Electron es un Chromium completo.

El camino de Linux queda igual: `xvfb-run -a -s "-screen 0 1920x1080x24"`
cuando no hay `DISPLAY`.

## Hecho cuando

- El comentario de uso de `scripts/e2e.mjs` y la frase del harness en
  `docs/plans/2026-09-25-e2e.md` dicen que en macOS la ventana no se muestra
  y que corren hasta 3 archivos a la vez.
- `npm run e2e -- smoke` y `npm run e2e -- worktrees` pasan. `worktrees`
  usa atajos y `returnToWindow`.
- Durante esa corrida, la app en primer plano no es Electron ni Crew
  (el proceso de System Events cuyo `frontmost` es true).
- Una corrida de varios archivos con la concurrencia nueva pasa
  (`E2E_SKIP_BUILD=1` si `dist/` ya está). Si un archivo falla solo en
  paralelo, el arreglo es el recurso compartido. Bajar el tope global es
  el último recurso, y no se vuelve a 1 para todo el runner.
