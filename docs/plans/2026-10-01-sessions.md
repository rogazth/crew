# Sessions — a lifecycle, and the tools a caller drives one with

Decided 2026-10-01, by walking one flow end to end: a Claude Code terminal
hands a job to a Codex session in a new worktree, waits for it, reads what it
did and gives it more. Every decision below is written at the step it governs.
Update the status table at the bottom as each one lands.

The case that started it: a terminal session asked an agent to do something
and could not hear back. `message_agent` delivers, but a terminal has no turns,
so nothing can be written back to it (decision 12 of the agent model). Cursor
has no MCP at all, so it cannot answer through a tool either. And every caller
already knows how to do the other half of the job — start a process, wait on
it, read its log — from the process tools.

## The words

Models have mixed these up before, so they are said the same way everywhere a
model reads them: `ARCHITECTURE.md`, the MCP `instructions()`, each tool's
description.

- **Agent** — a persistent identity: a name, a description, an autonomy, a
  message trail (its mailbox) and a history (its transcript). Crew owns it.
  `list_agents`, `create_agent`, `message_agent`, `continue_after_turn` stay as
  they are.
- **Session** — one provider CLI (claude, codex, opencode, cursor), with the
  provider's own conversation behind it. Disposable. It belongs to an agent
  (the session that runs the agent's turns), to the caller that started it (a
  *child*), or to nobody (a terminal the user runs).

> An agent outlives its sessions; a session is one provider CLI process and
> can be thrown away.

## The shape of it

The parent starts a session, waits on it and reads what it did. **The child's
reply is the end of its turn**: whatever it says last is its report. So the
child needs no tool to answer, which is what makes this work for a terminal
caller (who cannot receive a letter) and for a Cursor child (who has no MCP).

The tools are modelled on the process tools, on purpose: a model that has used
`start_process` + `wait_for_log` + `read_logs` already knows the moves, the
cursor and the bounded wait.

## The flow

### 1 · The tables are split

Today `sessions` holds both words: `kind` is `agent` or `terminal`
(`session.rs:158`), the agent's name and description sit next to the provider
it runs on, and the provider's own conversation hides in `provider_session_id`.

Migration 23 splits it:

| table | holds |
| --- | --- |
| `agents` | `id`, `workspace_id`, `name`, `description`, `notifications`, `autonomy`, `created_at`, `updated_at` — the identity |
| `sessions` | `id`, `workspace_id`, `kind`, `agent_id` (→ `agents`, NULL for anything that is not an agent's), `parent_id` (who started it; NULL is the user or nobody), `provider`, `model`, `provider_session_id`, `worktree`, `status`, `cursor`, plus the terminal's own name and tab order |

**An agent keeps one session, under the agent's own id.** Its turns run there,
so its transcript (`messages`), its mailbox and its routines keep their keys and
nothing that points at them moves: the migration copies identity into `agents`
and sets `agent_id = id` on the agent's row. A `Session` read for an agent
takes its identity from `agents` (one `LEFT JOIN`), and writes to the identity
go there. A terminal is a session with no agent. A child is a session whose
`parent_id` is whoever started it.

Kinds: `agent` (runs an agent's turns), `terminal` (a CLI the user drives in a
PTY), `child` (a CLI Crew drives turn by turn for whoever started it).

### 2 · The terminal calls `start_session`

```
start_session { provider, model?, prompt, worktree?: current | new | <branch>, name?, autonomy? }
  → { id, name, status: "starting", cursor: 0, worktree }
```

It returns at once. The parent is the caller.

- **Worktree.** `current` (the default) is the caller's own folder. `new`
  makes a branch `crew/<name>-<4 hex>` through `worktree::add`, the same path
  `create_worktree` takes. Anything else is a branch name or a worktree path:
  an existing worktree is used, otherwise `worktree::add` makes it.
- **Depth 1.** A child does not see `start_session`, nor any other session
  tool: its `Caller` is `Child`, and the session tools' `Audience` leaves it
  out. A child that wants help says so in its report.
- **A cap of 4 live sessions per parent.** Live is anything but `exited`. The
  fifth is refused with the four it has and how to stop one. The user is not
  capped.
- **Autonomy never grows.** The child takes the caller's autonomy, or `ask`
  when asked for. `full` from an `ask` caller is refused, the same rule
  `create_agent` follows (agent model, decision 2).
- **Provider and model** are checked against the same catalogue
  `create_agent` uses; a model under the wrong provider is answered with where
  it lives.

### 3 · The child runs its first turn

A child is driven by the same `TurnHost` an agent is, so its stream, tool rows,
approvals and transcript are the agent's code. What differs:

- **Its persona is the envelope**, not an agent's description:
  `Started by <parent> (<id>). Your final message of each turn is your report:
  end with what you did, what is left, and any question.`
- **It resumes instead of re-reading a tail.** A session *is* a provider
  session id, not necessarily a live process. Phase 1 spawns one process per
  turn and resumes the provider's conversation: `claude --resume <id>`,
  `codex exec resume <id>`, `opencode run --session <id>`,
  `cursor-agent --resume <id>`. The first turn starts a fresh one and binds its
  id. Agents keep the clean session per turn they have now.
- **Its tools** are the gateway as any caller's, filtered for `Child`: agents
  can be listed and written to, processes and tabs driven; nothing that makes
  sessions, agents or worktrees.

States: `starting → working ↔ idle`, `needs-input`, `exited`, `error`.

### 4 · The terminal calls `wait_for_session`

```
wait_for_session { sessions: [id…], since?: n | {id: n}, timeout_s ≤ 60 }
  → { result: "event" | "timed-out" | "nothing-running", sessions: [{ id, status, outcome, report, request?, cursor }], since: {id: n} }
```

It blocks until **any** of them ends a turn, asks for input or dies, and
answers with whichever did.

**The cursor is a position in the session's transcript**, the same number
`read_session` takes. Every event appends a block — a turn ending appends
`Report · turn N`, a stop `Stopped by …`, a crash its error, an approval its
card — so no two events share a position and **a turn that started and ended
between two waits is still there**: the wait compares positions, it does not
look at the status. Each event is a row in `session_events` (`session_id`,
`cursor`, `kind`, `report`, `request`).

- **Without `since`**, a wait starts from what this caller last saw of that
  session: Crew keeps the owner's `seen` cursor. So a parent that forgets the
  cursor still sees each turn once.
- **Nothing to wait for** — every named session idle, exited, errored or
  already waiting on an answer the parent has seen — answers at once with
  `nothing-running` and what to do about each, instead of sleeping a minute.
- **The report** is the turn's final assistant message, cut at 4 KB with a
  note to `read_session` for the rest.
- **Timed out** answers with the cursors to call again with, like
  `wait_for_log`. The MCP shim already waits `timeout_s + 10` for any tool
  that carries `timeout_s`.

### 5 · It reads what the child did

```
read_session { session, since?, max_bytes?, include_tools? } → { text, cursor, start, more }
```

Like `read_logs`: without `since` it reads the tail; with `since` what came
after it, up to `max_bytes` (16 KB, 256 KB at most); `cursor` is where this
read stopped, `more` says there is more. The transcript is rendered the way
the tail an agent is handed is (`working_set`): text as text, a tool as the one
line it did, numbered by position. `include_tools` adds each tool's output.

### 6 · It gives the child more

```
send_to_session { session, text, mode?: auto | queue | steer }
```

- **idle** (or `error`, whose provider conversation is still there): a new
  turn, resuming the child's conversation. Turn 2 remembers turn 1.
- **busy** (`starting`, `working`): queued in the session's mailbox, and the
  end of the current turn hands it over — the same drain an agent's box has.
  A wait counts an idle session with a message waiting as running: between
  the end of a turn and the drain that starts the next, it is about to be.
- **steer** (phase 3): into the running turn. Claude takes it: a turn's CLI
  lives as long as the turn, its stream-json stdin stays open, and a user
  message written there is read at its next step and folded into the turn
  (measured: `sleep 12`, a steer at 5 s, one `result` answering both). Children
  run Claude with `--replay-user-messages`, whose echo comes when the message
  is *read*, not when it arrives; that echo is where the steer's block goes in
  the transcript, and a steer the turn ended before reading goes in the box as
  the next turn. Codex, opencode and Cursor run each turn as one command, so a
  steer is refused with `queue` offered. Idle, a steer is just a new turn.
- **needs-input**: refused, pointing at `respond_to_session`. Queuing text
  behind a question would answer it with something nobody meant as an answer.
- **exited**: refused; start another.

### 6b · A turn that left something running

Claude can run a command in the background and end its turn on "started it,
I will report when it finishes"; in stream-json it then picks the conversation
up by itself when the command ends, with a second `result` (measured: a
`sleep 15` in the background, `result` at 10 s, the follow-up `result` at
28 s). Crew used to kill the CLI at the first `result`, so the follow-up never
happened. For a child that is the report its parent waits for, so a child's
turn now ends on the `result` that comes with nothing left in the background
(`task_started` with `is_backgrounded`, closed by `task_notification` or a
`task_updated` to a final status), or ten minutes after the last one, so a
server left running in the background cannot hold the turn for ever. An
agent's turn still ends on its first `result`: open, below.

### 7 · The child asks

A Claude child under `ask` stops at a tool with `needs-input`, exactly as an
agent does (`turns.rs:1290`). The wait answers with `outcome: "needs-input"`
and the request: its id, the tool, its input, or the questions.

```
respond_to_session { session, request_id, decision?: allow | always | deny, answers? }
```

**Who may approve.** Decision 10 of the agent model keeps an agent's
approvals with the user. A child is different: it was started to do the
parent's work with at most the parent's autonomy, so the parent answers — but
only within that autonomy. A `full` parent may allow; an `ask` parent may deny
and answer questions, and an `allow` from it is refused: the card waits for
the user in Crew. The user may always answer, in the window or with
`respond_to_session`.

Codex, opencode and Cursor run headless with no approval channel, so their
children never stop to ask; `ask` means codex's `workspace-write` sandbox and
opencode's own config, as it does for agents.

### 8 · It stops the child

```
stop_session { session }
```

Kills the CLI; the session is `exited`; the transcript stays in Crew and
`read_session` still reads it. Its queued messages are dropped.

### 9 · Who may touch a session

**Only the sessions you started.** `send`, `read`, `stop`, `respond` and
`wait` work on sessions whose `parent_id` is the caller, and the user may act
on any. A session that runs an agent's turns is addressed through
`message_agent`, never directly: reading another agent's transcript is the
channel the agent model closed (decision 14). A terminal is the user's CLI and
Crew does not drive it.

`list_sessions { mine? }` answers with what the caller started (the default),
or every session in the workspace with `mine: false`, each with its provider,
model, status, parent, worktree and cursor, and `self: true` on the caller's
own row.

### 10 · An agent as the parent

An agent may wait within its turn like anyone. It does not have to: when a
child's turn ends and its parent is an agent, the report also goes into the
agent's mailbox as a letter from the session, so the agent wakes with it when
it is idle, or after its current turn. A report the parent already saw through
`wait_for_session` or `read_session` is taken back out of the box before it is
delivered, so nothing is read twice.

### 11 · Nobody comes back

A session is a provider session id, so an idle one costs nothing but a slot
under the cap. **Idle children are reaped** after 30 minutes
(`CREW_SESSION_IDLE_MINUTES`): `exited`, with `Ended after N minutes idle` in
their transcript, and the slot is free.

### 12 · `crewd` restarts

The rows, events and transcripts are in SQLite. A child that was mid-turn when
the daemon stopped is resumed when it starts again — a turn that says Crew
restarted and to carry on — so a wait from its parent still ends in a report.
Its parent's next wait, with or without the cursor it held, carries on from
there. (A terminal parent's own CLI restarts with the window, and gets a new
token for the same session id: the ownership holds.)

### 13 · The window

Children are listed nested under the row of whoever started them: an agent, a
terminal, or at the top of the sessions section when the user did. A child's
tab is Crew's chat, like an agent's: the composer resumes it, its cards are
answered there, and stopping it there stops the turn, not the session.

## Decisions

| # | Step | Decision |
| --- | --- | --- |
| 1 | split | `agents` holds identity; `sessions` holds provider CLIs. An agent's session shares its id. |
| 2 | start | Returns at once; parent = caller. |
| 3 | start | Depth 1: a child sees no session tool. |
| 4 | start | 4 live sessions per parent; the user is not capped. |
| 5 | start | A child's autonomy is the caller's or lower, never higher. |
| 6 | run | One process per turn, resuming the provider's own conversation. |
| 7 | run | The envelope is the child's persona; its last message is its report. |
| 8 | wait | The cursor is a transcript position; every event appends a block. |
| 9 | wait | Without `since`, a wait starts from the owner's last-seen cursor. |
| 10 | wait | Nothing running answers at once. |
| 11 | send | auto/queue through the session's mailbox; steer is phase 3. |
| 12 | respond | The parent answers within its own autonomy; `ask` cannot allow. |
| 13 | own | Only the starter (or the user) touches a session; agents through `message_agent`. |
| 14 | agent | A child's report also reaches an agent parent's mailbox, unless already seen. |
| 15 | reap | Idle children exit after 30 minutes. |
| 16 | restart | A child interrupted by a restart is resumed. |
| 17 | steer | Claude takes a steer into its running turn, placed where its echo says it was read; the others refuse it. |
| 18 | run | A child's Claude turn waits for what it left running in the background, ten minutes at most. |
| 19 | run | `TurnHost::start` claims the session in one step: a message that came before the turn's CLI was up used to start a second turn beside it. |

## Phases

- **Phase 0** — this plan.
- **Phase 1** (required) — the split and the glossary; `start_session`,
  `list_sessions`, `wait_for_session`, `read_session`, `stop_session`.
- **Phase 2** (required) — `send_to_session` (auto, queue) and
  `respond_to_session`.
- **Phase 3** (if it fits cleanly) — live processes, for `mode: steer`: Claude
  with its stream-json stdin kept open, Codex through `app-server`.

## Open

- **An agent's background commands.** Decision 18 is for children. An agent's
  turn still ends on Claude's first `result`, and a command it backgrounded
  dies with the CLI. Same fix, different risk: an agent is the one most likely
  to have started a dev server that way. Worth doing with the same cap.
- **Codex steer.** `codex app-server` keeps a thread live and takes input
  mid-turn, but it is a protocol of its own (JSON-RPC, its own approval
  requests) and a provider adapter of its own. Not done; steer refuses codex.
- **Live processes between turns.** Nothing needs them yet: a turn's CLI is
  alive for the whole turn, which is when a steer can land, and the next turn
  resumes the conversation in a fresh process.
